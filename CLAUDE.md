# Tank Rush: Base Defense (YouTube Playables)

The title is `GAME_TITLE` ("Tank Rush") and `GAME_SUBTITLE` ("Base Defense") in `config.js`, shown on the continue screen (title large in yellow, subtitle smaller underneath, each shrunk to fit the playfield width with `fitTextSize()` in `save.js`). The page `<title>` in `index.html` ("Tank Rush: Base Defense") is set by hand: change it too when renaming.

A touch-first tank game inspired by classic 8-bit tank games, made for YouTube Playables. Plain HTML/CSS/JavaScript, no libraries, no build step to run it: `index.html` loads the scripts in order (the release build only copies and checks the files, see "Build and release"). Portrait layout: the playfield (13x21 tiles) on top and a bottom control zone with movement control on the left, HUD in the middle and FIRE on the right (swapped by the left-handed setting). Landscape layout (window at least as wide as tall): the same map shown turned a quarter clockwise (21x13 tiles on screen, the base on the left, the enemy spawns on the right) at (nearly) the full height, the HUD and controls in the side areas beside it; see "Screen layout". Everything is drawn on one canvas.

- `materials.js` – map tiles as data with their draw functions: empty, brick, concrete, metal, base, water (blocks tanks, not bullets), forest (drawn over tanks; tanks under it show faintly: enemies at `TERRAIN.forestEnemyAlpha`, the player at `forestPlayerAlpha`), sand (slower), ice (sliding). Each has a draw `layer`: "ground", "solid", then tanks and bullets, then "overlay" (forest). Draw functions take their colors from the current theme (`tileColors("brick")`); shapes and damage cracks are the same in every theme. Draw functions get `(x, y, size, cell, col, row)`. Brick is detailed (shaded bricks, specks, chipped corners, dark joints mixed from the theme's outline and mortar): each of its 4 looks (`BRICK_VARIANTS`, picked by position) is a cached picture; only damage is drawn live. Concrete (four beveled cast blocks) and metal (a beveled steel plate with four rivets) are cached pictures too, 3 looks each, with damage drawn live. Materials with `castsShadow` (brick, concrete, metal) get a soft shadow to the bottom-right (`drawWallShadows()` in `game.js`). Water, forest, sand and ice are detailed cached pictures that depend on which neighbours are the same material (`sameSides()`, `tileOutline()`), so patches join up and only sides touching other ground get a shore or edge; the sides are screen sides (`sameSides()` looks up the neighbour through `directionOnMap()`), so in landscape the shores still match the turned map while the picture stays upright; water ripples and sparkles are cached strips slid along with `gameTime`, offset by the tile's place on screen (`screenCell()`) so they run on across neighbouring tiles, forest crowns reach a little into neighbouring forest tiles (`FOREST_SPILL`). - `pause.js` – settings (sound effects, engine sound, left-handed, Drag/Cross move control), pause button (cached metal button with a gear, `paintPauseButton()` / `gearPath()`; it opens the pause menu, at the playfield's top-right, `placePauseButton()`; its tap area is at least `MIN_TAP_SIZE` (48 px) square, kept inside the playfield, `pauseTapRect()`) and menu (framed panel with a title plate and `drawUiButton()` buttons from `ui.js`; RESUME/BACK gold, the rest steel; positions from `pauseMenuLayout()`; on the main page the held upgrade badges with their names under the records, `drawPauseBadges()`, the panel grows downward for them; in landscape both pages are two columns, `pauseColumns()` / `settingsColumns()`, see "Screen layout"), system pause; `isPaused()` is also true while a rewarded ad loads or plays

Upgrade badges: `drawHudUpgradeBadges()` (one row, centered, sized so all 4 fit the HUD part; nothing while none are held), `drawUpgradeBadge()`, `paintUpgradeBadge()` (cached per badge, tier and size); `hudUpgradeBadges()` notices changes as the HUD is drawn (`badgeSeen`), so a badge bought in the shop flashes once the HUD shows again, and a lost one (armor broken, base steel used) flashes and fades out before it goes; `heldUpgradeBadges()` for the pause menu. `drawDebugTags()` (FREEZE, a generated level's seed) draws only with `DEBUG`. `field.x` / `field.y` are rounded to whole device pixels so the cached pictures stay sharp

## Rules when changing code
- All tunable numbers (speeds, prices, timers, gold values, volumes) go in `config.js`.
- Materials are data-driven in `materials.js`. A new tile should only need a config entry and a draw function.
- Enemy types are defined in `enemies.js`; levels are data in `levels.js`.
- Themes are data in `themes.js`. A new theme only needs an entry in `THEMES` (with every key the others have) and a level using its id. Draw code must not hard-code map colors: ask `currentTheme()`. Keep `screen` dark and `accent` bright, since the HUD text is white on the screen color.
- Visuals follow `STYLE.md`: light from the top-left, soft shadows to the bottom-right, readable at about 30 px tiles. Anything with many drawing steps, gradients or blur is painted once with `cachedPicture()` and copied each frame: no per-frame gradients or blur on large areas. Decoration uses seeded random or the tile position, never `Math.random`, so it doesn't flicker. Visual changes must not change gameplay, hitboxes or sizes.

## Themes and worlds
- Four themes: `standard` (olive earth with grass and stones, earthy brick), `jungle` (very dark moss and mud, mossy brick, dense forest), `desert` (warm sand with ripples, sandstone brick), `snow` (pale blue-white with drifts, ice-block brick, falling snow). Each has a display `name` for the banner ("World 1: Standard").
- Each level has a `theme` and a `world` number. When a level starts with a different theme than the level started before it, a `WORLD_INTRO` state shows "World 2: Jungle" for `WORLD_INTRO_TIME` seconds, then the usual "LEVEL X" intro. Never on the first level, and not again on a restart.
- The wall around the base is marked `cell.baseWall` (set in `setTile`) and drawn with the theme's `baseWall` colors.
- The accent color is only used for small details: the line at the top of the HUD, the "LV" label and the world banner. Shop, summary and game-over screens keep their own dark look.
- Ambient snow is computed from `gameTime` (no update step, stops on pause), at most 40 flakes, drawn after bullets and before the forest overlay. Turn it off with `AMBIENT.enabled = false`.
- Keep the code simple and commented. Don't add libraries.
- Don't add features that weren't asked for.

## Screen layout
- Chosen only from the game's own window size. `resize()` reads `window.innerWidth` / `innerHeight` (and the safe areas from the helper element) and calls `computeLayout(width, height, safe, ratio, leftHanded)`, which works out every rectangle without reading or changing anything else, then copies them into `field`, `controlZone` and `fireButton`. Narrower than tall is portrait, otherwise landscape. It runs on every `resize` event and from a `ResizeObserver` on the canvas. Never use `screen.width` / `height` / `availWidth`, `screen.orientation`, `window.orientation`, the `orientationchange` event, orientation locking or device posture APIs.
- A size change never resets anything: the level, shop, pause state, save, timers, effects, coins, power-ups and enemies go on as they were. Only the input is let go (`releaseForNewLayout()`: joystick, fire button, shop and menu scrolling, and held arrow keys), since the controls, and in a switch between portrait and landscape the directions, may have changed. A held key counts again once it is pressed anew: its auto-repeat is ignored until then (`cancelledKeys`). The cached pictures are painted again for the new size (`cachedPicture()` starts over when the tile size times the pixel ratio or the screen size changes). Nothing about the layout is worked out per frame.
- The turned playfield: the map stays 13x21 (`GRID_COLS` x `GRID_ROWS`) and the game logic, positions, hitboxes and saves never change. Only drawing and input go through the mapping in `game.js`:
  - `field.turned` is true in landscape and overlay; `field.cols` / `field.rows` are the tiles across and down on screen (13 x 21, or 21 x 13 when turned). `fieldRect()` is the playfield's rectangle on screen.
  - `mapToScreen(x, y)` turns a map position (in tiles) into screen pixels: in portrait `field.x + x * s, field.y + y * s`; turned a quarter clockwise `field.x + (GRID_ROWS - y) * s, field.y + x * s`, so map up is screen right, map right is screen down, map down is screen left and map left is screen up: the base (row 20) is on the left, the spawns (row 0) on the right. `tileToScreen(col, row)` is the top-left corner of a tile's square on screen, `screenCell(col, row)` its column and row on screen. All drawing of things on the map uses them: tiles, wall shadows, tanks, bullets, coins, power-ups, explosions, blasts and scorch marks.
  - Pictures are never turned: tiles, cracks, brick patterns, smoke and light are drawn upright, so the light stays top-left. Only things with a direction turn with the mapping: tanks are drawn facing `directionOnScreen(tank.facing)` (a picture already painted for that direction). Tile edges that depend on the neighbours look up the screen neighbour (`directionOnMap()` in `sameSides()`).
  - Input: keys, joystick and cross give a direction on screen; `currentDirection()` turns it back with `directionOnMap()` (screen right is map up, screen down is map right, screen left is map down, screen up is map left). This is the only place input is mapped.
  - Things placed on the screen, not the map, use `fieldRect()`: the border, ground shade, vignette, margins and their shadow, the pause button, snow, the tutorial hints, "ALL ENEMIES DESTROYED", the level intro and world banner. Text is never turned.
- `controlZone.mode`:
  - `"portrait"` (`portraitLayout()`): exactly as before, the control zone along the bottom in three parts, the playfield not turned. Checked against the previous version: every position, size and pixel is the same.
  - `"landscape"` (`sideLayout()`): the playfield, turned (21 x 13 tiles on screen), uses the full height less `LANDSCAPE.spacing` (8 px), centered. If the controls and the HUD don't fit beside it, the playfield gets one device pixel per tile smaller at a time (`sideLayoutAt()` with a smaller `maxTile` for `fitField()`), down to `minFieldShare` (85%) of its full-height size, and stays centered with margin art above and below; the first size that fits is used. Most phones held sideways get this: 800x360 at 25 px tiles instead of 26, 844x390 at 27 instead of 28, 852x393 at 27 instead of 29, and 1920x1080 at 78 instead of 81. There is no control zone (`controlZone.zone` is null), and the margin art fills the whole screen. The joystick or cross square (`moveBox`) sits in the bottom corner of the movement side, the fire button's square (`fireBox`) in the same place on the other side (swapped by left-handed), each at most `maxFieldGap` (0.5) control widths from the playfield's frame and `bottomMargin` above the bottom. A control is as big as the side allows, at most `controlShare` of the height and `controlMax`. The HUD is a framed display at the top of the movement side with the badge row under it: `sideHudSize()` picks the biggest font from `hudFontMax` down to `hudFontMin`, in one column or two (`SIDE_HUD`). The touch parts are the side areas from halfway between the HUD and the control down to the bottom.
  - `"overlay"` (`overlayLayout()`): used when the side areas are too narrow even with the smallest allowed playfield, i.e. the drawn joystick would be under `minControl` (96 px) or the HUD font under `hudFontMin`. That is 16:9 and 18.5:9 phones held sideways (667x375, 640x360, 740x360), 16:10 and squarer screens (1440x900, 1280x800, 1024x768, 600x600). Their overlay playfield is about as big as a side layout's would be, since the HUD strip takes some height. A slim HUD strip runs along the top (one row of text, with the badge slots at its right end), the turned playfield sits under it, and the controls are drawn see-through (`overlayAlpha`) over the playfield's bottom corners, `overlayControlShare` of its shorter side.
- Very wide or very tall windows: the playfield stays centered, the rest is margin art, and the controls stay next to the playfield.
- The pause button is always at the playfield's top-right corner, drawn at least `pauseMinSize` in landscape, and its tap area is at least 48 px.
- Overlay screens (level result, game over, campaign complete, the continue screen, the pause menu and settings) are laid out around a middle point in units (`overlayFrame(top, bottom)`, with their extents in tiles):
  - Portrait: over the playfield in tiles, as before.
  - Landscape and overlay: centered on the screen, in a unit (`controlZone.overlay.unit`) the size an upright playfield's tiles would have (`uprightTileSize()`: the height less the spacing, over `GRID_ROWS`; so menus and the shop don't grow with the turned playfield's bigger tiles), but at least `minTouch / SMALLEST_MENU_BUTTON`, so the smallest menu button is 48 px, and no wider than the screen. The shop's unit is worked out the same way. A screen that is then taller than the window scrolls (`overlayScroll`): drag it or use the mouse wheel, and a button chosen with the keyboard is scrolled into view (`scrollOverlayTo()`). A tap that turns into a drag presses nothing. The scroll goes back to the top when the screen or the pause page changes.
- In landscape (and overlay) the pause menu (both pages), the level summary, the game over screen and "CAMPAIGN COMPLETE" are two-column panels instead (`fitTwoColumnPanel()` in `game.js`), so they fit without scrolling. The panel is `LANDSCAPE.panelWidth` (17) units wide (a screen can pass its own `width` and the left column's share, `split`), centered on the screen, with the title plate on top; title and panel together are at most `panelShare` (92%) of the screen's height. Two columns are used only where that width is at most 92% of the screen's width (`isTwoColumnLayout()`): in nearly square windows (600x600, 520x500) the columns would be too narrow for the text at 14 px, so those keep the one-column screens, which fit their taller window without scrolling. If a panel is taller than 92%, text and spacing get smaller together (`panelSizes(k)`), in 1% steps down to `panelMinScale` (75%), with text never under `minText` (14 px) and buttons never under `minTouch` (48 px). Only if it still doesn't fit the screen does it scroll like the other screens. Each column is centered in the taller one's height. Everything is worked out from the current screen size whenever the screen is drawn or tapped, so a resize or a turn of the phone moves it without closing or resetting anything.
  - Pause menu (`pauseColumns()` / `drawPauseColumns()` in `pause.js`): "PAUSED" on top; left the best score and highest level, then a divider and the held upgrade badges in a list, each with its name; right the buttons stacked: RESUME (gold, 1.8 units tall), RESTART LEVEL, SETTINGS (1.4 units), and with `DEBUG` CLEAR SAVE.
  - Settings page (`settingsColumns()` / `drawSettingsColumns()` in `pause.js`): "SETTINGS" on top; left SOUND EFFECTS and ENGINE SOUND, right (55% of the width, its labels are longer) CONTROLS and MOVE CONTROL, and the gold BACK centered under both; Up/Down goes through them in that order. The controls are still drawn behind the panel, so a change shows right away: with the controls beside the playfield the panel stays between them (`settingsPanelWidth()`), but at least `LANDSCAPE.settingsMinWidth` (15.5) units wide so "CONTROLS: RIGHT-HANDED" keeps 14 px; in the overlay layout they're under the panel, as before.
  - Level summary (`summaryColumns()` / `drawSummaryColumns()`; the rows come from `summaryRows()`, shared with portrait): "LEVEL X COMPLETE" on top; left one line each for enemies destroyed, gold from coins and the three bonuses (missed ones greyed out with 0), all in one font size that fits both columns (`panelRowFont()`); right "Gold this level" and "Your gold" on the faint gold strip, and CONTINUE under them (`layoutScreenButton()` places the tap area there).
  - Game over (`gameOverColumns()` / `drawGameOverColumns()`; the buttons' labels and actions come from `gameOverButtonItems()`, shared with portrait): "GAME OVER" on top; left the broken star plate with the final score beside it, "Your base was destroyed" (if it was), a divider and the records; right RETRY LEVEL X (if offered) and START OVER, with the ad line halfway between them. The right column gets 58% of the width so the buttons' second lines stay readable, and the buttons are at least `minText` * 4 tall (the second line is a quarter of the height).
  - "CAMPAIGN COMPLETE" (`campaignColumns()` / `drawCampaignColumns()`; the buttons come from `campaignButtonItems()`, shared with portrait, and are drawn by `drawCampaignButtons()`): the title on top; left the gold star plate with "TOTAL SCORE" and the score under it; right (55% of the width) "CONTINUE TO ENDLESS" (gold, only with `ENDLESS_ENABLED`) and "PLAY AGAIN", 1.6 units tall.
  - Checked in the browser with all four upgrade badges, `DEBUG` on, the base destroyed and a 6-digit score: at 640x360, 800x360, 844x390, 915x412 and 1024x768 all five fit without scrolling at full size (pause menu 322 px tall, settings 257, summary 219, game over 233, campaign complete 229; buttons 48-64 px, every text and button label at least 14.4 px with the longest setting labels). The settings panel never covers the side controls (532 px wide at 800x360, 574 at 844x390). At 800x300 the pause menu shrinks to 75% and fits the screen (6 px over the 92% box because of the DEBUG button); at 800x240 it scrolls, while the game over (92%) and campaign complete (96%) shrink and fit. At 600x600 and 520x500 all of them use one column and fit.
- The shop in landscape is a card grid (`shopGridPlace()`): 3 columns if 3 cards of `shopCardWidth` units fit, otherwise 2, each card at most `shopCardMax` units wide. The header and the "next level" panel sit side by side above it and START sits under it. The unit makes START at least 48 px, and the list scrolls as before.
- Sizes in landscape: the drawn joystick and cross are at least 96 px, every touch target is at least 48 px, with 8 px between controls. In portrait too every button is at least 48 px (`buttonHeight()`; at 360 px wide the 1.4-tile menu buttons would be 37.8 px), and the rest keeps its old sizes.
- With `DEBUG` on, `layoutSelfTest()` runs on load. It computes the layout for `LAYOUT_TEST_SIZES` (360x800, 412x915, 800x360, 915x412, 768x1024, 1024x768, 1920x1080, 3440x1440, 360x1280, 1280x360, 600x600, 520x500, and the phones held sideways 844x390, 932x430, 667x375), right- and left-handed, and logs every rectangle (a collapsed `[Layout] 915x412: landscape, OK` group with a table, and a line like "playfield 21x13 tiles (turned), tile 27 px (28 at full height), ..."). It checks that:
  - the playfield is upright 13x21 in portrait and turned 21x13 in landscape and overlay, every map tile lands on a tile of its own inside it, the base is on the left and the spawns on the right when turned (at the bottom and top in portrait), each map direction moves on screen the way tanks are drawn facing, and input turns every direction back (`mappingProblems()`);
  - everything is on the screen;
  - nothing drawn overlaps (except the overlay controls over the playfield);
  - there are 8 px between controls;
  - touch areas don't overlap each other or the HUD;
  - the joystick and cross are at least 96 px in landscape (48 in portrait);
  - touch targets are at least 48 px, and in landscape so are the menu buttons and the shop's START.

  A failing size gets a `console.warn`. The last line says "[Layout] self-test: all 15 sizes pass (both hands)" or names the sizes that failed. All 15 pass.

## Levels
- Format (`levels.js`): each level is `{ name, theme, world, map, enemies }`. `map` is `GRID_ROWS` strings of `GRID_COLS` letters (13x21, set in `config.js`), legend `.` empty, `B` brick, `C` concrete, `M` metal, `W` water, `F` forest, `S` sand, `I` ice. `enemies` lists type names from `enemies.js` in spawn order; every 4th spawn flashes and drops a power-up (`POWERUPS.flashingEnemyEvery`).
- The game places these itself, and the map must keep them `.`: the base (`BASE_TILE`, column 6, row 20) and its brick wall (row 19 columns 5-7, row 20 columns 5 and 7), the player start (`PLAYER_START`, column 4, row 20) and the spawn points (row 0, columns 0, 6, 12). `loadLevel` clears those tiles anyway.
- `checkLevels()` in `game.js` runs on load, only when `DEBUG` is true, and warns (`console.warn`) for each level about: wrong map size, unknown letter, theme or enemy type, a blocked fixed tile, a spawn point that can't reach the base (flood fill with `floodFill` from `levelgen.js`; brick open, concrete/metal/water blocked), and more than `LEVEL_MAX_FILLED` (35%, `config.js`) of the tiles brick/concrete/metal/water. All 20 levels pass.
- The level name shows under "LEVEL X" in the intro.
- Map design rules: symmetric left/right (small asymmetric touches are fine); the base must be reachable from every spawn point (brick counts as passable, water/concrete/metal do not); water as rivers or ponds (never single tiles) with at least 2 crossings; at most about 35% of the tiles filled (forest, sand, ice don't count); keep the area around the base and the player start open. Enemy types are spread through the list; difficulty rises from level to level.
- Level plan (all done). After level 20 the "CAMPAIGN COMPLETE" screen shows (see "Campaign complete"), then endless mode continues with generated levels (see "Endless mode").
  - World 1, standard: 1 First Steps (10), 2 Crossfire (12), 3 The River (13), 4 Steel Wall (14), 5 Fortress (16)
  - World 2, jungle: 6 Deep Green (14, big forest patches, 3 metal blocks in front of the base), 7 Riverbanks (15, two rivers with forest banks, 3 crossings, 3 metal blocks in front of the base), 8 Hidden Giants (16, 3 heavy, concrete hidden in forest), 9 The Maze (17, brick/forest maze, a pond), 10 Jungle Heart (18, 6 heavy, river, forest center, metal on the flanks)
  - World 3, desert (more fast tanks): 11 Dunes (16, big sand patches, few walls), 12 Ruins (17, concrete/brick ruins, open lines), 13 The Oasis (17, center pond split by a sand path, sand around), 14 Sandstorm (18, 10 fast, vertical sand lanes), 15 Desert Fortress (19, 7 heavy, concrete/metal fortress)
  - World 4, snow: 16 First Frost (17, big ice patches), 17 Thin Ice (18, ponds ringed by ice, brick bumpers), 18 Frozen Maze (18, ice corridors, metal/brick walls), 19 Pine Forest (19, 7 heavy, ice and forest, small pond), 20 Final Winter (20, 8 heavy, river, fortress, ice, forest)
  - (numbers in brackets: enemy count)

## Level generator
- `levelgen.js`: `generateLevel(seed, themeId, difficulty, world, name)` returns a level in the `levels.js` format (plus `seed` and `difficulty`), so the game loads it like a hand-made one. Difficulty is capped to 1-15. It is deterministic: all randomness comes from a seeded mulberry32 (`makeRandom`), never `Math.random`. All numbers are in `GENERATOR` in `config.js`.
- Theme extras are data in `themes.js` (`generatorTiles`): `patches` (how many), `weights` (river, pond, forest, sand, ice), `patchSize` and `riverWidth`. Standard: small rivers, few ponds, forest; jungle: large forest patches, rivers (1-2 rows); desert: sand patches, a pond sometimes; snow: ice patches, ponds, some forest.
- Steps, all on the left half (columns 0-6), then mirrored: at most one river first (rows `GENERATOR.riverRows`, one gap of `crossingWidth` tiles away from the middle column, so 2 crossings after mirroring; the gap and the tiles above/below it are kept open), then ponds of 3-6 tiles and forest/sand/ice patches, then wall segments and small blocks with the difficulty's brick/concrete/metal mix and cluster count (`GENERATOR.walls`). Walls and water keep one tile of space from each other. A solid cluster that would push brick/concrete/metal/water over `maxSolidShare` (35%, the base wall included) is not placed. Clear zones around the base, the player start and the spawn points stay empty (the base gets its brick wall).
- Reachability: a flood fill checks that each spawn point can reach the base (water, concrete, metal block; brick counts as open). On failure it tries seed+1, up to `GENERATOR.maxAttempts` (20), then uses an open layout with a few brick pillars.
- Enemies: 16 to 24 by difficulty; basic and fast from the start (`fastShare`), heavy share rising from `heavyShareMin` to `heavyShareMax`. Each type is spread evenly through the list (seeded wobble). Power-up carriers are still every 4th spawn (game.js).
- `levelAt(index)` in `game.js` returns the level (hand-made or generated, cached); use it instead of `LEVELS[index]`.
- `GENERATED_MODE` in `config.js` (false by default, for testing the generator from level 1): level N uses seed `GENERATOR.baseSeed + N`, difficulty N (max 15), and the theme changes every `levelsPerTheme` levels (`themeOrder`, world number counts up). The run never ends.

## Campaign complete
- After the level 20 summary, "CONTINUE" shows `GAME_STATE.CAMPAIGN_COMPLETE` (`showCampaignComplete()` in `game.js`): title, total score and two menu buttons (tap, or Up/Down + Enter/Space, after `BUTTON_DELAY`): "Continue to Endless" (shop, then level 21) and "Play again" (run cleared, `newGame()`). No effects or animations.
- Once per run (`campaignShown`, reset by `newGame()`, set by `continueSavedRun()` when the saved run is past level 20). Not in `GENERATED_MODE`.
- With `ENDLESS_ENABLED = false` (`isLastLevel()` true) it is the end of the run: only "Play again", and the saved run is cleared. There is no separate "YOU WIN" screen.
- On showing it: `updateRecords()`, `progress.campaignComplete = true`, `writeSave()`, `sdk.sendScore(score)`.
- Buttons are drawn with `drawMenuButton()` (`game.js`), shared with the continue screen. In landscape the screen is two columns (see "Screen layout").

## Endless mode
- `ENDLESS_ENABLED` in `config.js` (true by default). After level 20 the "CAMPAIGN COMPLETE" screen offers "Continue to Endless": the shop, then generated levels (`isLastLevel()` is false). With false, that screen has only "Play again".
- Level N (21, 22, ...) is `endlessLevel()` in `game.js`: seed `GENERATOR.baseSeed + N`, theme rotating through `GENERATOR.themeOrder` (standard, jungle, desert, snow) every `levelsPerTheme` (5) levels starting with standard at 21, difficulty `min(15, ENDLESS.startDifficulty + floor((N - 20) / ENDLESS.levelsPerDifficulty))` (5 + (N - 20) / 2), name "Endless N", world number continuing from 5. The usual world banner shows on each theme change.
- Enemy speed/fire scaling is the same capped `ENEMY_SCALING` as for hand-made levels.

## Rewarded continue (game over)
- The game over screen (`GAME_STATE.LOST`, `drawEndScreen()` / `drawGameOverButtons()` in `game.js`) has two buttons of the same size (9 x 1.6 tiles), stacked under the panel (tap, or Up/Down + Enter/Space, after `BUTTON_DELAY`), each with a smaller second line (`drawUiButtonTwoLines()` in `ui.js`): the gold "RETRY LEVEL X" (X = the level just lost) with the play-triangle ad badge and "Watch an ad, keep your upgrades" under it, and the steel "START OVER" with "Back to Level 1" (it clears the saved run and calls `newGame()`). Alone, "Start over" moves to the top place, turns gold and keeps its second line (without it the lone button looked bare). Each line shrinks until it fits the button, checked down to 280 px wide screens. Between the buttons a small status line: "3 RETRIES LEFT" (only with a limit and more than one left), "LOADING AD..." while waiting, or the failure message; otherwise nothing. In landscape the screen is two columns, the buttons in the right one (see "Screen layout").
- All these texts are in `UI_TEXT.gameOver` (`config.js`), written as they show (button labels in capitals); `{level}` and `{left}` are filled in.
- The retry button shows only when `canOfferContinue()`: inside Playables (`sdk.inPlayables()`: `ytgame` exists and `ytgame.IN_PLAYABLES_ENV`; with `DEBUG` also outside, where the ad is simulated), a checkpoint exists, the lost level is level 2 or later (level 1's checkpoint is the same as "Start over", so no ad for nothing) and the run has continues left (`continuesLeft()`). Otherwise only "Start over".
- Limit: `REWARDED_CONTINUES_PER_RUN` is `null` (no limit) by default; `null` or `Infinity` means no limit (`hasContinueLimit()` false, `continuesLeft()` Infinity, the count is never shown), a number means at most that many per run. `continuesUsed` is counted and saved either way, so a limit can be added later by setting a number.
- Checkpoint: `takeCheckpoint()` (`save.js`) runs in `startLevel()` right after the level index is set, before the base steel is used up: `progress.checkpoint = { level, gold, score, upgrades, seed }` (level 1-based, `upgrades` the whole shop object, so tiers, lives bought, held armor and base steel; `seed` only for generated levels). Every level start replaces it (also a restart or a debug level key). It's saved with everything else.
- Pressing it calls `requestContinueAd()` (only from this tap or key): `sdk.requestRewardedAd(REWARD_ID_CONTINUE)` ("continue-from-level", no user data). Until the answer `gameOverScreen.waitingForAd` is set: `isPaused()` is true (nothing updates), both buttons are dimmed and off, and `Sound.setAdPlaying(true)` mutes all sound (it goes on top of the SOUND EFFECTS and ENGINE SOUND settings and YouTube's audio setting).
- The answer (`finishContinueAd()`): true -> `continueFromCheckpoint()`: `continuesUsed` + 1, lives `START_LIVES_AFTER_CONTINUE` (3), gold, score and upgrades exactly as in the checkpoint (the failed attempt's gold and score are dropped), then `startLevel()` with the same level: the same map and enemy list (generated levels come from the `generatedLevels` cache, a DEBUG "H" level stays), fresh enemies, a repaired base, base steel used again if it was held, no world banner, no shop: the "LEVEL X" intro, then play. False -> "NO REWARD THIS TIME", rejected or thrown -> "AD NOT AVAILABLE", each for `AD_MESSAGE_TIME` (2 s); both buttons stay, no continue is used. No answer within `AD_WAIT_LIMIT` (90 s, counted in `loop()` by `updateAdWait()`, so system pauses don't count) is "AD NOT AVAILABLE" too, so "Start over" can't stay off for good; a later answer is ignored (`adRequest`).
- `loseGame()` works as before (records, `writeSave()`, `sdk.sendScore(score)` with the failed attempt's score), except the saved run: while a continue is offered it is `checkpointRun()` (the checkpoint's level, gold, score and upgrades, `START_LIVES_AFTER_CONTINUE` lives, `continuesUsed` + 1) instead of null. Closing the game on the game over screen and opening it again then offers the usual "Continue from level X" (shop before that level), and that counts as a continue. A continue sends no score (the next level end or game over does).
- `continuesUsed` is saved with the run (`rememberRun()`), restored by `continueSavedRun()` and reset to 0 by `newGame()` ("Start over", "New game", "Play again" on "CAMPAIGN COMPLETE").
- The YouTube docs don't say whether a rewarded ad sends `onPause` / `onResume` or audio events; both are handled: an `onPause` during the ad saves and stops the loop as usual, and an answer that arrives while paused starts the level intro, which waits for the resume.

## YouTube Playables SDK
- The SDK script (`https://www.youtube.com/game_api/v1`) loads before any game code.
- `firstFrameReady()` is called once the first frame (loading screen) is drawn.
- `gameReady()` is sent only when the player can interact (after the "LEVEL 1" intro), once.
- Pause/resume follow only `ytgame.system.onPause` / `onResume` via `setSystemPause()` (`pause.js`); the page's visibility, focus and blur are never used. While paused the game loop stops completely, input is let go, audio is suspended, sound-file downloads stop and a resize waits for the resume.
- Sound respects `ytgame.system.isAudioEnabled()` and `onAudioEnabledChange`: YouTube's mute is the only overall sound switch. The in-game SOUND EFFECTS and ENGINE SOUND settings each turn off only their part.
- Every SDK call must be safe when the SDK is missing (running locally): go through the `sdk` wrapper in `game.js` (checks `ytgame` exists, try/catch). The exception is `saveData` / `loadData`, which live in the `Save` object in `save.js` (same checks, plus `ytgame.IN_PLAYABLES_ENV`).
- `onPause` also saves the game (`writeSave()`), since the player may not come back.
- Rewarded ads: `sdk.requestRewardedAd(rewardId)` wraps `ytgame.ads.requestRewardedAd` (a public-preview API) in try/catch: it resolves true only if YouTube answered exactly true, false for any other answer, and rejects when the call throws, `ytgame.ads` is missing or YouTube rejects (the error may be undefined). Outside Playables it rejects, or with `DEBUG` simulates an ad (`DEBUG_AD`). Only called from the game over screen's continue button, see "Rewarded continue". No interstitial or other ads.
- Scores: `sdk.sendScore(score)` sends the run's total score (`{ value }`, always a whole number ≥ 0) when a level is completed (`finishLevel`) and when the game is lost (`loseGame`: lives gone or base destroyed) and when the "CAMPAIGN COMPLETE" screen shows (`showCampaignComplete`), never per frame. All three call `updateRecords()` first and send through `submitScore()` (`save.js`), which holds the score until the save has loaded, so the highest score YouTube shows always equals the saved `bestScore` (the docs require the best score sent to match the game save). Without the SDK it only logs `sendScore: <value>` when `DEBUG` is on.

## Saving
- `save.js`: `Save.save(data)` / `Save.load()` store one small JSON string. Inside Playables (`ytgame` exists and `ytgame.IN_PLAYABLES_ENV`) via `ytgame.game.saveData` / `loadData`, otherwise `localStorage` (key `SAVE.key`), all in try/catch, at most `SAVE.maxBytes` (500 KiB). Nothing saved or broken JSON gives no save and the game starts fresh. Every `version` from 1 up loads (older ones, and a newer one after a rollback). Loading (`startLoadingSave()`) only stores the answer and the game loop takes it (`updateSaveLoading()`), so nothing happens while YouTube has the game paused. The start-up waits on the loading screen for the answer or `SAVE.loadTimeout` (3 s) of unpaused time, then starts fresh, and a save that comes later is merged in (`mergeLateSave`). A failed load is tried again at the next save. Every loaded value is checked (`applySaveData`, `readSavedRun`, `readSavedCheckpoint`, `readSavedUpgrades`); a bad run or checkpoint is dropped.
- Format (`SAVE_VERSION` 1): `{ version, settings: { soundEffects, engineSound, leftHanded, controlType }, bestScore, highestLevel, tutorialDone, campaignComplete, checkpoint, run }`. `campaignComplete` (hand-made level 20 ever completed), `settings.engineSound`, `checkpoint` and `run.continuesUsed` were added without a version change: older saves without them load as false, true (engine sound on), no checkpoint and 0. `settings.soundEffects` replaced the overall `settings.sound`: an older save with `sound` off loads with both sound effects and the engine off. `run` is null or `{ level, gold, lives, score, upgrades, continuesUsed }`, where `level` is the level the shop leads to (1-based), `upgrades` is the shop's `upgrades` object (tiers, lives bought, held armor, base steel) and `continuesUsed` the rewarded continues used in the run. `checkpoint` is null or `{ level, gold, score, upgrades, seed }`, how the run stood when the current level started (see "Rewarded continue"); on load it is only taken over together with a saved run of the same level (otherwise the level-1 checkpoint made at start-up stays; every level start makes a new one anyway). Change `SAVE_VERSION` when the format changes.
- `writeSave()` saves everything; in the shop it takes the run again first (`rememberRun()`), so purchases are kept. Nothing is saved before `loadData` succeeded (`progress.loaded`): the save waits (`saveWanted`) and is written once loading worked. Saves happen only on events, never per frame:
  - shop opened (`openShop`): the run
  - level completed (`finishLevel`): `updateRecords()` (best score, highest level = level number played)
  - game over (`loseGame`): records, run cleared, or set from the checkpoint while a rewarded continue is offered (`checkpointRun()`); "Start over" there and "New game" on the continue screen: run cleared
  - "CAMPAIGN COMPLETE" shown: records, `campaignComplete`, run cleared only without endless mode; "Play again" there: run cleared
  - a setting changed (pause menu), `onPause`
- Start-up: `init()` sets up level 1, shows the loading screen (`GAME_STATE.LOADING`), calls `firstFrameReady()` and `loadSaveAtStartup()`. Saved settings and `tutorial.done` are applied. With a saved run, `GAME_STATE.CONTINUE_PROMPT` shows "Continue from level X" / "New game" and `gameReady()` is sent then (`sendGameReady()`); otherwise the "LEVEL 1" intro starts as before. Continue (`continueSavedRun()` in `game.js`) restores gold, lives, score, upgrades and `continuesUsed` and opens the shop before the saved level; no mid-level state is saved.
- Best score and highest level show on the game over screen and under the pause menu buttons. With `DEBUG` on, the pause menu has "CLEAR SAVE (DEBUG)" (`clearSave()`: records, `campaignComplete`, run and tutorial reset, settings kept), and the loaded save is logged (`[Save] loaded: ...`).

## Audio
- The AudioContext must be unlocked by a user gesture. `audio.js` creates/resumes it on pointerdown, pointerup, touchstart, touchend, click and keydown (phones only count the end of a touch as a gesture, so touchstart alone left the first tap silent), plus a silent buffer for older iPhones; it also resumes from the iPhone "interrupted" state, but never while the game is system-paused.
- Every sound is built in code from oscillators and filtered noise with a short attack and an exponential decay (no clicks), in `SOUNDS` in `audio.js`; a few are played from sound files instead once those have loaded (see the next points). Sound names: playerShot, enemyShot, brickHit, brickDestroy (the hit that breaks a brick; made in code it's the brick hit), concreteHit, metalHit (metal walls and bullets blocked by the player's shield or respawn blink), heavyHit (a heavy tank hit but not destroyed), explosion, baseDestroyed, coin, powerUp (last note depends on the power-up type, passed as the third argument), armorBreak, purchase, cantAfford, levelStart (a ~1.3 s heroic tune: warm square/triangle brass layers in D major, a D bass, snare, a boom and a crash on the held top note; notes from `melody()` / `heldNote()`, which hold instead of fading; played by `setState()` whenever the "LEVEL X" intro starts: after the world banner, on a restart, not on the very first intro before any tap since audio isn't unlocked yet), levelComplete, gameOver, uiTap. A wall's hit sound is its material's `hitSound` (`materials.js`), and the hit that destroys it plays its `destroySound` if it has one (brick: brickDestroy).
- Sound files: `sounds/` has WAV files (credits in `CREDITS.md`) for playerShot, enemyShot, brickHit, brickDestroy and explosion, listed per effect in `SOUND_FILES.files` (`config.js`), and `engine_loop.wav` for the engine (`SOUND_FILES.engineLoop`). `loadFiles()` fetches and decodes (`fetch` + `decodeAudioData`) all of them at once in the background when the AudioContext is created on the first input. Nothing waits for them, so `firstFrameReady()` / `gameReady()` are not delayed. An effect plays one of its files once one has loaded, and its sound made in code until then, or for good if the files fail to load (a failed effect file warns, a missing engine loop doesn't: the engine made in code plays).
- Variations: several files in an effect's list; a random one plays each time, never the same one twice in a row (`pickFile()`). Each file plays at a playback rate of 1 +/- `SOUND_FILES.pitchVariation` (4%); the varied sounds also get the usual volume variation.
- File volumes: one per effect in `SOUND_FILES.volumes` (1 = the file as it is), used instead of `AUDIO.volumes` while the file plays; everything after that (effects volume, softener, mute, limiter, sound limit, repeat gap) is the same as for the sounds made in code. Starting balance, measured through the same phone-speaker filter: at 1 the files were 3-9 dB louder than the sounds made in code they replace, so the two loudest were lowered (enemyShot 0.7, brickDestroy 0.6); the engine file was about 12 dB quieter than the engine made in code, so it's at 4.
- Load time: the 6 files are 696 KB (the engine loop is half of it). Measured with a local server throttled to 180 KB/s (about Fast 3G): all loaded and decoded in 4.9 s, the shots and the brick hit within 1.1 s; at 50 KB/s (about Slow 3G) 17.5 s. Until then the sounds made in code play.
- Chain: each sound -> its volume (`AUDIO.volumes`, or `SOUND_FILES.volumes` for a file) -> `AUDIO.effectsVolume` -> a gentle low-pass (`softenAbove`) -> mute -> limiter (`AUDIO.limiter`, a DynamicsCompressor; it adds about +4 dB make-up gain) -> speakers. The engine goes through `ENGINE_VOLUME` into the same mute and limiter. The volumes were balanced by measuring each sound through a phone-speaker filter (high-pass at 400 Hz): taps and hits quietest, shots, coins and pickups in the middle, explosions and jingles louder, base destroyed loudest, engine clearly below everything.
- All sound is off while YouTube's audio is off (`isAudioEnabled()` / `onAudioEnabledChange`) or a rewarded ad loads or plays (`Sound.setAdPlaying()`, game over screen): `isEnabled()` is false, the mute fades to 0 and the engine stops. The SOUND EFFECTS setting (`settings.soundEffects`) only stops new effects from playing (`effectsSettingOn()` in `play()`), and ENGINE SOUND only the engine.
- At most `AUDIO.maxSounds` play at once, the same sound doesn't start twice within `AUDIO.repeatGap` (40 ms), and shots, hits, explosions and coins vary a little in pitch and volume each time (`pitchVariation`, `volumeVariation`).
- Engine: one set of nodes (sawtooth + square a few cents apart + quiet noise, low-pass, a volume LFO for chugging) made the first time the player drives and reused; only its fade, pitch and LFO rate change. `updateEngineSound()` in `game.js` runs every frame from `loop()` (also while paused) and calls `Sound.setEngine(driving, pitch)`: driving = playing, not paused, player alive and steering. It fades in over `fadeIn` and out over `fadeOut` (150 ms). `enginePitch()`: higher per tank speed tier, lower on sand (`speedFactor` below 1), higher on ice (`slippery`). Off on pause, menus, end screens, a destroyed tank, YouTube audio off, a rewarded ad and the ENGINE SOUND setting off; a system pause silences it at once and it only comes back once the player drives again.
- Engine from the file: once `engine_loop.wav` has loaded, the engine is that file looping seamlessly (`buildFileEngine()`: an AudioBufferSourceNode with `loop = true` -> `SOUND_FILES.volumes.engine` -> the same fade), with the same fades, pause and mute rules; its pitch changes go to the playback rate. If it loads after the engine made in code was built, that one fades out and stops (`retireEngine()`) and the file takes over.

- The JavaScript is not minified, so it stays readable for review (served compressed it is much smaller anyway). There is no platform layer: one build, for YouTube Playables (outside Playables it runs with localStorage saves and no ads).
- With `DEBUG` false no debug code runs: the debug keys, tags, logs, the layout self-test, the level check, the simulated ad and "CLEAR SAVE (DEBUG)" all check `DEBUG`. Only real warnings (`console.warn`) are logged.
- To release: run `py build.py`, test `dist/` served over http, then zip the contents of `dist/` (not the folder itself) and upload it. Add every new asset that isn't hand-written code to `CREDITS.md`.

## Playables rules
Keep these true for every change (YouTube Playables certification):
- Pause only from `ytgame.system.onPause` and resume only from `onResume` (`setSystemPause()` in `pause.js`): no `visibilitychange`, `document.hidden`, blur/focus or `pagehide`. A system pause stops the loop, input, sound, the engine, sound-file downloads and resizes (done on resume); `onPause` saves. The pause button and Escape only open the pause menu.
- Inside Playables save only with `ytgame.game.saveData` / `loadData`; localStorage only without the SDK. No save before `loadData` succeeded (`writeSave()` waits, `submitScore()` holds the score until then). Saves stay under `SAVE.maxBytes` (500 KiB); every older save version loads. The best score sent with `sendScore` always equals the saved `bestScore` (`updateRecords()` first).
- YouTube's mute is the only overall sound switch: the pause menu has only SOUND EFFECTS and ENGINE SOUND. Nothing plays while YouTube audio is off or an ad loads/plays.
- No external calls, links, fonts or CDNs (only the SDK script), no `eval` / `new Function` / string timers, workers, WebAssembly, clipboard, `navigator.language`, `screen.*` or orientation APIs. Relative paths, file names of letters, digits, `_`, `-`, `.`, every file under 512 KiB.
- Touch, mouse and keyboard all work everywhere; Escape closes the pause menu, settings and dialogs and is never `preventDefault`-ed. Buttons are at least 48 px (`buttonHeight()`), with hover, pressed, focused and disabled looks (`ui.js`); small text has at least 4.5:1 contrast.
- Rewarded ads only from the clearly labeled game over button ("RETRY LEVEL X"), never automatic; "START OVER" is always there.
- No exit button, sharing, external links, agreements or login screens. Everything in English (`UI_TEXT`).
